# LLM 评审协议（阶段一）

> Claude 在训练循环第 4 步以"资深游戏设计师"视角评审地图。**阶段一核心维度：解谜的乐趣（巧妙解法的趣味性）**。
> 评审结果写入 `data/maps/<name>.json` 的 review 字段。评审标准随用户试玩反馈演进——用户反馈与评审分明显背离时，调整权重或增删维度（先与用户确认）。

## 评审输入

- 地图存档（`data/maps/<name>.json`：mapData + designIntent + validation）
- 硬门报告（必须已全部通过，否则不评审）
- 经验库 `data/experience.md` 与最近反馈（对照参考）

## 评审流程

1. **先玩一遍**（对 mapData 做心智模拟：按玩家视角走关键路径，含鬼的追捕行为）
2. 逐维度打分（0-5），每项给一句话理由
3. 给出整体结论与改进建议

## 维度（阶段一）

| # | 维度 | 考察点 | 高分信号 |
|---|---|---|---|
| 1 | **解谜趣味性**（核心，权重最高） | 最优解是否非显而易见？是否存在"想通时眼前一亮"的瞬间？ | 解法需要绕路/回头/时机把握，不是一路直走 |
| 2 | **决策深度** | 玩家在关键点是否有真实取舍（威胁近路 vs 安全远路；先拿钥匙还是先探索）？ | 每个决策点都影响结局；不止一个有意义的选择 |
| 3 | **设计意图达成度** | 落地是否兑现了 designIntent 的谜题核心？ | 设计意图的每个机制都在玩法中真实起作用 |
| 4 | **威胁真实性** | 鬼是否真实压迫决策？被盯时刻是否紧张？甩鬼是否靠技巧（穿门/转角）而非运气？ | 威胁有预警、有对策、对策有技巧含量 |
| 5 | **公平性** | 信息是否足够？死亡是否可归因于玩家决策而非随机/不可知？ | 视野内可预判威胁；没有"鬼瞬移贴脸"式的冤死 |
| 6 | **涌现新颖性** | 机制组合或布局是否出乎意料？与训练集已有图是否有区分度？ | 出现训练集中未见过的谜题结构或组合 |

## 量化信号（辅助，来自验证报告）

- 解法特征：`detourSteps`（绕路量）/ `backtrackCount`（回头）/ `keyDepth`（钥匙序深度）——阶段一这些值越高越可能"巧妙"，但要小心为绕而绕
- `ghostSeenSteps` 与"甩鬼发生的位置"是否在设计意图的决策点处
- 最优步数与"直觉最短路径"（relaxed 下界）的差

## 评审输出模板

```js
{
  score: 0-5,                      // 整体评分
  dims: {                          // 各维度
    puzzleFun:  { score: 0-5, note: '...' },
    decision:   { score: 0-5, note: '...' },
    intent:     { score: 0-5, note: '...' },
    threat:     { score: 0-5, note: '...' },
    fairness:   { score: 0-5, note: '...' },
    novelty:    { score: 0-5, note: '...' }
  },
  highlight: '最精彩的瞬间/设计',
  weaknesses: ['不足1', '不足2'],
  suggestions: ['改进建议（具体到位置/机制）'],
  verdict: 'pass | revise | reject'
}
```

- `pass`：可直接试玩
- `revise`：有小问题，修改后复验
- `reject`：核心设计不成立（但硬门已过的情况下很少见）

## 评审纪律

1. **不许用设计意图的话复述打分**：评审必须指出"设计意图想达成的效果"在机制层面**真实发生**的证据（具体到格子/时序）
2. **不许事后诸葛亮**：评估玩家能否在迷雾+有限信息下发现解法
3. **威胁必须真实**：如果最优解完全不接触威胁（或威胁可被无损绕过），threat 维度 ≤2
4. **区分度**：与训练集已归档地图结构雷同时 novelty ≤2，并说明雷同在哪
