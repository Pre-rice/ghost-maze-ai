# 训练方法论 · 生成-验证-评审-反馈循环

> 本文件是训练循环的操作协议。**基本逻辑由用户把关**；本协议的任何重大修改（新环节、评估标准调整、新要素引入）必须先与用户讨论确认。

## 一、为什么是这条路线（历史背景）

原仓库 `ghost-maze` 曾用"约束构造 + 进化搜索 + 人工权重评估"路线（阶段 0–7，已归档到 `archive/ai-pipeline-v1` 分支），实证失败：

1. **评估函数 Goodhart**：人工设计的代理指标（绕路量/回头次数等 band 分）被进化游戏化，进化提升仅 1.7%（fitness 0.659 vs 随机基线 0.648）。
2. **求解器是瓶颈**：带鬼 A* 状态空间爆炸 → 超预算降级贪心 → 大量可解图被误判不可解 → 只选出"贪心就能过"的同质化图。
3. **搜索空间太小**：10×10 只能装 2 锁 2 环，进化在微小的参数空间里打转，无法涌现复杂设计。

**结论**：评估"什么是有趣"不能靠人工权重，生成"有趣设计"不能靠小参数搜索。改为：
- **生成**：LLM（Claude）以游戏设计师身份直接产出地图——创意开放，不预设骨架（如旧的 spine/口袋/环结构）
- **把关**：可解性、无伤性等客观硬门由算法判定，不可妥协
- **评审**：Claude 以设计师视角评审软质量（趣味性、决策、新颖性）
- **反馈**：真人（用户）试玩是最终裁判，评审标准随反馈演进
- **积累**：每张图全记录 → 经验库 → 下一轮生成参考 → "训练"的本质

## 二、阶段一生成约束（严格限定）

| 维度 | 限定 | 说明 |
|---|---|---|
| 尺寸 | 10×10 | 宽高均 10 |
| 模式 | death-loop | `gameMode:'death-loop'`，`initialStamina:100` |
| 墙类型 | EMPTY/SOLID/DOOR/LOCKED | 禁止 ONE_WAY/GLASS/LETTER_DOOR |
| 实体 | 钥匙 + 鬼 | 禁止按钮/楼梯/多层（`multiLayerMode:false`） |
| 起点 | `startPos:{1,8}`（regular） | 左下 3×3 出生房自动揭示 |
| 核心 | 解谜围绕鬼 | 钥匙序、路线取舍、穿门甩鬼时机都必须与鬼的威胁互动 |

`npm run validate` 会按此约束校验（`--no-stage1` 可跳过要素检查，供阶段二调试）。

## 三、训练循环（每张图的完整流程）

### 第 0 步：读取记忆
- 读 `data/experience.md`（全部历史教训）与最近 3-5 条试玩反馈（`data/feedback/`）
- 明确本轮要"练什么"：避免重复已证失败的模式、延续成功的模式

### 第 1 步：构思设计意图（生成层，Claude 输出）
产出**设计意图**，至少回答：
- **谜题核心**：玩家解这道题时，关键顿悟/决策是什么？（一句话）
- **玩家决策点**：玩家会在哪面临选择？每个选项的代价/收益是什么？
- **鬼的剧本**：鬼在哪、玩家何时被盯、如何甩掉？（威胁必须真实存在且可破解）
- **机制组合**：钥匙序？穿门甩鬼？取舍环？组合出的新意是什么？
- **设计参数**：钥匙数、锁门数（keys 值）、鬼数、DOOR 数及大致布局

> 设计意图是涌现的载体：**先想清楚谜题再落地布局**。评审时逐条对照。

### 第 2 步：落地为 mapData JSON（生成层）
- 按 [map-format.md](map-format.md) 的格式规范输出 `{ mapData, designIntent, name }` 存档
- 落地过程尊重设计意图；发现落地不了时**修改布局方案**而不是硬塞

### 第 3 步：硬门验证（验证层，算法判定）
```bash
npm run validate -- <map.json>
```
四道硬门，任一不过即淘汰并**分析原因**：
1. **结构合法**：形状/边界/实体/阶段一要素约束
2. **结构可解**：无鬼 BFS 钥匙约束可达
3. **无伤可通**：带鬼 A* 存在零伤路径（stamina 内）
4. **威胁实质**：最优解路径被鬼盯 ≥1 步（鬼不是摆设）

不过 → 回到第 1 步重新构思（或小改后重试）；同一思路连续失败 3 次 → 换思路。
**注意 confidence='approx' 时最优性未保证**，解法特征只作参考。

### 第 4 步：LLM 评审（评审层）
按 [review-protocol.md](review-protocol.md) 的 checklist 评审，输出：
- 各维度评分（0-5）+ 一句话理由
- **改进建议**（具体到位置/机制）
- 与训练集已有图的区分度检查（防同质化）

### 第 5 步：用户试玩（反馈层，最终裁判）
```bash
npm run sharecode -- <map.json>   # 得到分享码，粘贴进游戏试玩
```
用户试玩后反馈：谜题巧不巧？卡在哪？哪里无聊？死得冤不冤？
```bash
npm run feedback -- <map.json> "<评语>" <得分>
```

### 第 6 步：归档与提炼（经验库）
- 地图 + 设计意图 + 验证报告 + 评审 + 反馈 → `data/maps/<name>.json`（全记录）
- 提炼教训 → 追加 `data/experience.md`（成功模式 / 失败模式 / 设计铁律）
- **经验库是训练的核心资产**：它让下一轮生成站在历史之上

### 迭代策略
- **质量优先于数量**：宁要 3 张精心打磨的图，不要 20 张平庸的图
- **分主题训练**：一个阶段集中练一种谜题结构（如"穿门甩鬼"），成型后再换
- **难度阶梯**：从单一谜题 → 组合谜题 → 多决策点

## 四、什么算"训练好了"

阶段一训练完成的标准（与用户确认后定）：
- [ ] 生成的地图稳定通过四道硬门（无需反复返工）
- [ ] 用户试玩评分 ≥ 8 分的地图有可复现的设计模式（已沉淀进经验库）
- [ ] 涌现出至少 1 种用户没想到的精妙解谜设计
- [ ] 评审标准与用户偏好对齐（评审分与用户分趋势一致）

达成后再与用户讨论：是否引入新要素（阶段二）、是否封装为自动化生成（API 脚本）。

## 五、规则

1. **硬门不可妥协**：任何软评估理由都不能让不过硬门的地图进入试玩
2. **用户是最终裁判**：用户试玩反馈 > LLM 评审 > 求解器特征 > 任何权重
3. **诚实记录**：失败的地图也要归档（失败模式是训练数据的一部分）
4. **不造假**：验证报告、评审、反馈必须真实对应实际运行结果
