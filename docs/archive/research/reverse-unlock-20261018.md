# 反向开门：机械构件成立，但不递补交付

2026-10-18。原设想是让同一扇0门的开门方向影响后续追逐，而非再次增加提前开门或困鬼次数。研究原件见[冻结清单](../../../data/manifests/reverse-unlock-20261018.json)，没有玩家试玩标签、上架或新增训练。

两室／两端原型中的反例没有省略：初稿8步完全不用0门；增加资格门后，五个有解代表均可从两向开启，单项改图270份中204份有解，也均有不用指定反向开启的完整通关。其余66份穷尽无解，没有预算未知；这不证明所有反向开门点子不可行。

后来借上鬼、下鬼及单向退出关系，实现反向开启对全部通关必要的26步构件。直接开启的安全前缀无续解，全部最优无重合、去终点安全。然而其余流程仍近乎固定，不以此作挑战交付。加入B的24步稿使同一鬼先暂留右侧，再被引出让开观察口；仍是已有安置流程的增量。

上侧安排的34步稿有普通门停位和未来B操作的联系。原图最优四条、两种含停顿轨迹；三处门属性组合删除后仍34步、八条最优，所检上鬼横移、两处B和开0均对全部通关必要。单项和组合分别保存，不保留仅为机关数量的门。不过上侧路线本身会强制带出正确停车，新增必要关系不能充当新增规划深度。

为增加真实替代而改变单向入口的31步稿又出现反例：整条最优可略过左B；禁止反向开启仍可最优通关。预期的第二项安排没有按设想保留。没有用该稿覆盖旧构件，也没有因31步或唯一鬼轨迹把它当好图。

《寄存》随后获“普通的引鬼困鬼、很容易”反馈。该评述只属于《寄存》，不能转成这些未交付稿的真人质量标签；设计者据此停止以同类停位／顺序增量递补交付。下一步从是否摆脱逐个困鬼的整体安排审起，不继续靠更多门和步骤修补这一批稿。

证据限制：初稿 `probe.mjs` 的数字门类型监控误用了普通门类型，相关禁止事件查询不作结论；后续脚本使用正确类型并保留原输出。部分新增顶部方格的外缘在后稿显式补墙，早稿未经边缘与分享往返交付验收。各稿原生规划及已执行的最优边界不等于完整QA；没有声称编号、实际入场与分享码已全部核验。
