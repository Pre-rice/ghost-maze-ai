# 当前评审约定

评审对象先经过固定版本游戏引擎的证书重放。旧的被鬼看见至少一次不再是通用硬门。

1. 检查机关是否实际改变可行策略，记录替代解与反例。
2. 检查真实观察下的信息公平、理解后的执行成本和不必要重复。
3. 每批提供少量已经验证的候选，用户试玩后选择 A 更好、B 更好或相近，可附原因。
4. 隐藏生成来源和设计说明再作首次比较，区分试玩评价与只看演示。
5. 缺失的偏好保持缺失，不把机器分数、设计意图或一般肯定填成人工标签。

现已提供 [第一批成对试玩](../examples/review-batch-01/README.md)：运行 `npm run review`，在本地页面试玩、记录与导出。支持 A、B、平局、暂时无法判断；记录试玩进度和此前是否了解解法。数据格式与校验见 [反馈工作流](review-workflow.md)。

2026-09-30 首批反馈为“全部太简单、解法显而易见”，见 [复盘与选题调整](review-batch-01-findings.md)。正式候选应先经过内部质量评审，不将明显冗余的对照图交给用户凑配对。相对标签与是否达到目标质量分开保存；整批拒绝或太简单的评价不能丢失在平局/胜出标签里。

完整指标、损失与批次建议见 [训练方案第 5 节](ai-training-plan.md#5-高质量评价如何落地)。旧 LLM 自评协议原文保存在 [归档](archive/llm-workflow-v1/docs/review-protocol.md)。
